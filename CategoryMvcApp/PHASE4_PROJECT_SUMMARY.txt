UNDERSTANDING VIEWMODEL ROLES
═══════════════════════════════════════════════════════════════════════════════

Entity Models (Models/) vs ViewModels (ViewModels/):

ENTITY MODELS:
├─ Represent database structure
├─ Include relationships, navigation properties
├─ May have sensitive/implementation details
├─ Direct mapping to database tables
└─ Not suitable for views (too complex/exposed)

VIEWMODELS:
├─ Represent view data requirements ONLY
├─ Lightweight, focused on what view displays
├─ Security: Don't expose sensitive properties
├─ Can include derived/calculated fields
├─ Type-safe, strongly-typed in views
└─ Easier to maintain (decouple view from entity structure)

WHY SEPARATE?
✓ Security (don't expose all entity properties)
✓ Flexibility (view structure independent of database)
✓ Performance (include only needed data)
✓ Testability (easier to mock ViewModels)
✓ Maintainability (changes to DB don't break views)

MAPPING PATTERN:
    Entity (Movie)           ←→  ViewModel (MovieCardViewModel)
    ├─ Id ──────────────────→ ├─ Id
    ├─ Title ───────────────→ ├─ Title
    ├─ PosterUrl ──────────→ ├─ PosterUrl
    ├─ ReleaseDate ────────→ ├─ ReleaseDate
    ├─ Description ────────→ ├─ Description (truncated)
    ├─ TrailerUrl ─────────X (not needed for grid)
    ├─ DurationMinutes ────X (not needed for grid)
    ├─ Shows (navigation) ─X (included in DetailVM, not CardVM)
    └─ CreatedAt ─────────X (internal detail)

DATA ANNOTATIONS REFERENCE (Applied Throughout)
═══════════════════════════════════════════════════════════════════════════════

VALIDATION ATTRIBUTES:
├─ [Required]                       – Field is mandatory
├─ [StringLength(200)]              – Max characters allowed
├─ [Range(min, max)]                – Numeric range validation
├─ [Url]                            – Must be valid URL format
├─ [MinLength(1)]                   – Minimum items in collection
├─ [RegularExpression(@"^[A-Z]\d+$")] – Seat number format (A1, B12, etc)
└─ [EmailAddress]                   – Email format validation

DISPLAY ATTRIBUTES:
├─ [Display(Name = "Movie Title")]  – User-friendly label
├─ [DataType(DataType.Date)]        – Date format (no time)
├─ [DataType(DataType.DateTime)]    – Full datetime
├─ [DataType(DataType.Currency)]    – Currency formatting
├─ [DataType(DataType.Url)]         – URL field hint
└─ [DisplayFormat(DataFormatString = "{0:C}")] – Custom format

INTEGRATION POINTS:
✓ Model Binding     – Automatic deserialization from JSON/forms
✓ Validation        – Server-side checked in [HttpPost] actions
✓ Client-Side       – Unobtrusive validation JS (jquery.validate)
✓ View Rendering    – Labels/formats from [Display] attributes
✓ IntelliSense      – Type hints in editors

AJAX INTEGRATION FLOW (Detailed)
═══════════════════════════════════════════════════════════════════════════════

The DTOs (ReserveSeatsRequest/Response) enable AJAX integration:

CLIENT SIDE (jQuery):
1. User selects seats on SeatSelectionViewModel page
2. jQuery builds request:
   {
       "showId": 5,
       "seatNumbers": ["A1", "A2", "B3"]
   }
3. $.ajax POST with JSON.stringify():
   $.ajax({
       type: "POST",
       url: "/Booking/ReserveSeats",
       contentType: "application/json",
       data: JSON.stringify(request),
       success: function(response) {
           if (response.success) {
               // Redirect to confirmation
               window.location = "/Booking/Confirmation/" + response.bookingId;
           } else {
               // Show error
               alert(response.message);
           }
       }
   });

SERVER SIDE (ASP.NET Core):
1. Controller receives request via model binding:
   [HttpPost]
   public async Task<IActionResult> ReserveSeats([FromBody] ReserveSeatsRequest req)
   {
       // req.ShowId = 5
       // req.SeatNumbers = ["A1", "A2", "B3"]
   }

2. Process booking:
   ├─ Validate show exists
   ├─ Check seats available (race condition prevention)
   ├─ Create Booking in transaction
   ├─ Add BookedSeats
   ├─ Calculate total
   └─ Return JSON response

3. Return response:
   return Json(new ReserveSeatsResponse
   {
       Success = true,
       Message = "Booking confirmed",
       BookingId = 42
   });

CLIENT RECEIVES: { "success": true, "message": "...", "bookingId": 42 }

BEST PRACTICES APPLIED IN PHASE 4
═══════════════════════════════════════════════════════════════════════════════

✓ SOLID PRINCIPLES
  • S (Single Responsibility): Each ViewModel has one purpose
  • O (Open/Closed): ViewModels are open for extension, closed for modification
  • L (Liskov Substitution): ViewModels follow consistent interfaces
  • I (Interface Segregation): Only include needed fields per ViewModel
  • D (Dependency Inversion): DTOs enable loose coupling with AJAX clients

✓ CLEAN CODE
  • Descriptive names: MovieCardViewModel, SeatSelectionViewModel, etc.
  • Single responsibility: Each ViewModel represents one view
  • No duplication: Reusable nested ViewModels (SeatCategoryPriceViewModel)
  • Well-documented: XML /// comments on every class and method
  • Proper formatting: Consistent indentation, line breaks, naming

✓ SECURITY
  • Don't expose full entities (risk of leaking sensitive data)
  • Strongly-typed views prevent injection attacks
  • HTML encoding automatic in Razor (@Html.DisplayFor)
  • Data annotations validate input server-side

✓ PERFORMANCE
  • Include only necessary fields (lighter than full entities)
  • No unnecessary navigation properties loaded
  • DTOs optimized for JSON serialization
  • Clear mapping patterns for efficient LINQ projections

✓ MAINTAINABILITY
  • Strong type checking (compile-time errors caught)
  • IntelliSense support (developers know available properties)
  • Decoupled from entities (DB changes don't break views)
  • Documented mapping patterns (easy to add new ViewModels)
